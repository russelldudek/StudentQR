# Google Apps Script Setup

Use [Code.gs](./Code.gs) as the backend for the Student QR page.

## Sheet headers

Your `Students` tab should have a first row with these exact column names:

- `First Name`
- `Last Name`
- `QR_ID`
- `Status`
- `Admitted At`

Optional but supported:

- `Bringing Guest`

## Deploy

1. Open [script.new](https://script.new/) while signed into the Google account that can edit the sheet.
2. Replace the default script with the contents of [Code.gs](./Code.gs).
3. Save the project.
4. Click `Deploy` -> `New deployment`.
5. Choose type `Web app`.
6. Set `Execute as` to `Me`.
7. Set access to `Anyone` or `Anyone with the link`.
8. Copy the `/exec` URL into the app's `Apps Script Web App URL` field.

## Configure Once: Eve And Helpers

The updated frontend and backend must both be deployed before this flow works.
The web app URL is generated by Google during deployment; a Sheet URL is not a
backend URL. Do not reuse an unrelated dance's endpoint.

1. On the published HTTPS app, enter the dance's compatible roster setup once.
2. Click **Save shared dance and create links**. The server checks the Sheet
   headers without writing attendance, then stores the shared setup in Script
   Properties. An unsupported backend or incompatible Sheet does not issue links.
3. Give **Eve's private admin URL** only to Eve. It opens the saved dance's
   dashboard with Setup available. Bookmark this URL, including its `#key=` part.
4. Give helpers only the **Shareable check-in link** or its generated QR. Their
   phones open Scanner with the dance and current roster loaded, without Setup,
   a password, or sign-in. They tap **Start camera scan** and allow camera access.
5. Eve can change setup through her link and save it centrally. Devices refresh
   configuration and roster every eight seconds while Scanner/Dashboard is
   visible. These are polling updates, not an instantaneous push connection.

Each backend stores one active shared dance. Use a separate deployment/project
for another independent dance, or deliberately update this dance for all devices.
The admin and helper keys are distinct random 256-bit bearer credentials; anyone
holding a link can use that role. Helpers cannot edit setup, assign IDs, or change
global test mode. The QR is generated in the browser with
[QRCode.js](https://github.com/davidshimjs/qrcodejs), not sent to a QR image service.
The server stores a hash of the admin key, never returns it to helpers, and ignores
caller-supplied Sheet settings in shared requests.

After first shared initialization, old embedded-setup links and unkeyed API calls
are intentionally refused for that deployment. Distribute the new helper link.
Initialize a fresh deployment before distributing its URL; the first setup is a
one-time bootstrap, and subsequent saves require the existing admin key. Keep the
admin URL safely: recovery/rotation needs the Google script owner, not a helper.
A lost initial response can be retried with the same keys while the page is open.
Reload Eve's URL if a concurrent admin save makes the revision stale.

**Homecoming draft limitation:** `Ticket Checklist` has its intake headers on row
5 and a combined student/guest layout. It is not the generic row-1 `Students`
roster described above. The read-only combined projection remains disabled at the
API boundary; this link feature does not enable admission from that intake,
provision status/timestamp columns, or migrate student data. Its reviewed reader
and attendance integration must be completed before live Homecoming activation.

## Expected behavior

- `GET ?action=list` returns `{ rows: [...] }`
- `POST { action: "list", config }` also returns `{ rows: [...] }`
- `POST { action: "assignQrIds", config }` fills blank `QR_ID` cells without overwriting existing ones
- `POST { action: "admit", qrValue, config }` matches the `QR_ID`, writes `Status=Admitted` and `Admitted At`, and blocks repeat scans when the row is already admitted
- `POST { action: "setTestMode", testMode, config }` changes test mode globally for that dance roster
- `POST { action: "saveEvent", config, adminToken, helperToken }` initializes a shared dance once
- `POST { action: "saveEvent", eventId, token, revision, config }` updates it using the admin key
- `POST { action: "getEvent", eventId, token }` loads role-specific configuration
- Shared `list`, `admit`, `assignQrIds`, and `setTestMode` requests include `eventId`, `token`, and `revision`
- If `testMode` is enabled in config, admit validates the code without writing attendance changes

## Notes

- The frontend sends the full sheet configuration with both `GET` and `POST`.
- New QR IDs are generated with an event-based prefix plus a random suffix, and existing `QR_ID` values are left untouched.
- If the roster still fails to load, redeploy the script after changes and make sure the copied URL ends in `/exec`, not `/dev`.
